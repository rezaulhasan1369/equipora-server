# Equipora D0.6 investigation — 2026-11-18

Base: deployed commit `843a5e4`. This report is the predeployment investigation
snapshot. The owner has approved this diagnostic deployment subject to security
validation. It includes no frontend, credential/user/permission, hosting, Atlas
network-rule, or production environment-variable change.

## Confirmed findings

- The deployed D0.5 record is `database_health_failure`, stage `connect`, category
  `connection_timeout`; the corresponding invocation lasted 5080.89 ms. The app
  returned its own HTTP 503, meaning its catch block executed.
- `src/db.ts` explicitly sets `serverSelectionTimeoutMS: 5000`. Installed driver
  code in `src/sdam/topology.ts` creates a server-selection timer and raises
  `MongoServerSelectionError` when it expires. That is the approximately
  five-second deadline, rather than a Netlify execution termination.
- Effective local options are: selection timeout 5000 ms, socket-connect timeout
  30000 ms, socket timeout 0, wait-queue timeout 0, automatic address-family
  selection enabled, no forced IPv4/IPv6 family, and no configured operation
  timeout. No shorter application or function deadline is configured in source.
  Netlify documents a 60-second synchronous function execution limit.
- Read-only Atlas metadata confirms the local URI points to the inspected
  cluster, which is FREE, IDLE and not paused. The network list still has three
  restricted entries (one /32 and two /24 entries), with no unrestricted entry.
  These entries alone cannot prove an egress mismatch. No source IP for the
  failing Netlify connection or Atlas denial record has been established.
- Local credentials use the dedicated application user, the URI database is
  `equipora`, and the app explicitly pings `equipora`. Local driver connect/ping
  succeeds. The effective auth source is `admin` after Atlas TXT resolution.
  Pre-connect URI parsing alone does not include TXT-derived overrides.
- Live local SRV and TXT queries succeed. All three discovered nodes resolve
  IPv4 and pass TCP and certificate-verified TLS. No IPv6 records were returned
  for those nodes locally. That absence is not an error or proof about Netlify.

## Production configuration comparison: not yet verified

The prior dashboard inspection confirmed nonempty masked Production values and
Functions scope for the MongoDB URI and diagnostic key. No authenticated Netlify
API/CLI secret-reading session is available. Unmasking values into browser/tool
output would violate this task's secrecy requirement, so it was not attempted.

The new comparison uses HMAC-SHA256 keyed by the existing diagnostic key. A local
helper computes four domain-separated proofs entirely in memory: normalized
cluster target, configured/application database, noncredential authentication
settings, and selected nonsecret connection options. It sends only those proofs in
an authenticated HTTPS POST. The server independently computes them and returns
only four equality booleans. Proofs, secrets and configuration values are never
logged or returned. No new secret is required or stored.

The final security review removed full-URI and password-derived proofs: those
could have allowed a diagnostic-key holder to test credential guesses. Passwords
and mechanism properties never affect the accepted proof fields. Tests verify
that changing a password does not alter any proof or comparison result. No
password-equality or complete URI-equality claim can therefore be made.

Authentication comparison covers the declared source/mechanism and whether the
user is the intended dedicated user, rather than arbitrary username equality.
It is pre-TXT, not a claim about successful authentication or runtime TXT
contents. Connection options cover TLS policy, family selection, replica-set and
direct/load-balanced modes, proxy presence, and the principal timeout settings.
Unlisted URI options and credential equality remain unverified. TXT resolution
is separately probed. Local-versus-production remains pending deployment.

## Locally prepared implementation

- `src/db-network-diagnostics.ts`: private configuration proofs; bounded Atlas
  SRV/TXT and A/AAAA queries; TCP followed by verified TLS for each address family.
  No MongoDB writes or authentication attempts are made by these network probes.
- `src/app.ts`: adds `POST /api/health/db/diagnostics`, protected by the existing
  diagnostic key. It accepts only the exact proof schema, rejects query/target
  inputs, returns `no-store`, sanitizes early parser/CORS errors, permits one
  in-flight run and enforces a 30-second cooldown per warm function instance.
  Existing health endpoints and MongoDB client options are unchanged.
- `scripts/compare-production-db.ts`: fixed production URL, no arguments or
  secret command-line values, no redirects, 10-second client deadline, and a
  strict whitelist of output fields/statuses. Not run against production.
- `tests/db-network-diagnostics.test.ts`: proof separation; rejection of arbitrary
  targets, nonpublic addresses, and insecure configurations; credential-oracle
  prevention; output sanitization; resolver cancellation;
  socket closure; missing/invalid keys and configuration; malformed bodies;
  concurrent calls and cooldown. Existing tests remain unchanged.
- This report records evidence and the next approval boundary.

Probe constraints:

- Only the configured Atlas `mongodb+srv` target is supported. Non-Atlas URIs,
  custom SRV services, proxies, insecure TLS and custom certificate configurations
  return unsupported rather than producing misleading probes.
- SRV targets must remain under the configured Atlas DNS suffix and use port
  27017. Maximum three servers, first returned address per family per server.
- Nonpublic, local, link-local, mapped, special-purpose and reserved address
  ranges are rejected before transport. IPv6 handling is deliberately conservative
  and excludes transition/special-purpose prefixes, rather than risking a probe
  into a local network. No request data can select a probe target.
- Each DNS/TCP/TLS step has a 1200 ms deadline. Network work has a 6000 ms abort
  budget; DNS is cancelled and sockets destroyed on cancellation or completion.
- Results contain fixed statuses and booleans only. No hostnames, addresses,
  records, TXT contents, certificates, credentials, raw exceptions or stacks.
- Cooldown is per instance, not a distributed rate limit. These are temporary
  operator diagnostics; remove them after diagnosis in a separately reviewed change.
- Short probes can time out during transient latency. A probe timeout alone is
  not definitive proof of a blocked path. Sampling does not test every address.

## Interpretation and proposed next action

The timeout's source is identified; the underlying production connection failure
is not. A production URI mismatch, DNS differences, TCP reachability, TLS
negotiation, or later MongoDB handshake/server selection remain possible. Local
success rules out a universally unavailable cluster, not a production-specific
problem. Restricted Atlas entries support investigating network filtering but
do not confirm it.

Another owner-approved diagnostic deployment is necessary with current access.
After deployment approval, validate existing health/key handling and run:

`node --import tsx scripts/compare-production-db.ts`

That helper sends the existing key in a header and configuration proofs in the
body, never as URL/query parameters. Do not print its request headers/body.

Use the result to choose the smallest correction:

1. Configuration mismatch: privately reconcile the intended production setting;
   obtain approval before changing it. Do not rotate credentials automatically.
2. SRV/TXT or A/AAAA failure: isolate runtime DNS before changing URI format.
3. IPv4 works and IPv6 fails: check driver/runtime family selection; consider a
   narrowly justified IPv4 option only after production evidence supports it.
4. TCP fails: compare trusted runtime egress evidence with Atlas rules. Do not add
   an observed temporary IP, broad provider ranges, or unrestricted access.
5. TCP succeeds but TLS fails: investigate negotiation/certificate trust without
   disabling certificate or hostname checks. Atlas filtering can also interrupt
   handshakes; a TLS timeout is not proof of a certificate issue.
6. TCP/TLS succeed yet existing driver selection fails: focus on MongoDB hello,
   replica-set discovery, authentication and selection behavior. The prepared
   probe deliberately does not claim to validate those MongoDB protocol stages.

Do not increase timeouts as a speculative fix. No infrastructure correction or
hosting migration is justified yet. If restricted network access proves to be
the issue, Netlify Free has no guaranteed static-egress feature; an allowlist-safe
architecture would need a separately approved trusted stable-egress host. This
investigation has not established a guaranteed reliable free-hosting replacement.
