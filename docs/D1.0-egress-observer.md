# D1.0 controlled egress observation

This deployment adds an operator-only, single-use Netlify Function. It does not
alter the Express API, MongoDB configuration, Atlas rules, credentials, frontend,
or hosting. It performs no database writes.

## Security controls

- POST `/.netlify/functions/egress-observer` requires the existing diagnostic key
  before payload decoding, parsing, storage access, or network probes. Other
  requests receive the same generic 404 response.
- Strict JSON payload: at most 2 KiB, exactly nonce, timestamp, rules and MAC.
  Only 1-16 IPv4 rules with prefixes /24 through /32 are accepted. There are no
  destination, URL, port, connection-string, or probe-option inputs.
- A domain-separated HMAC authenticates the entire private snapshot and nonce.
  Timestamp tolerance is two minutes. Existing diagnostic authorization remains
  unchanged. The snapshot is sent only over authenticated HTTPS to the function;
  no reusable configuration/credential-comparison oracle is provided.
- An atomic Netlify Blobs `onlyIfNew` write admits at most one execution across
  function instances for this experiment. It stores only `{consumed:true}` under
  a fixed experiment identifier. Storage failures fail closed, with a two-second
  request deadline and SDK retries suppressed. A consumed marker is never reset,
  including after failed observations. No additional permanent secret is needed.
- The observer expires at 2026-11-18 00:30 UTC. It is inaccessible afterwards even
  with a valid key. No caller can extend this window or reset the one-use gate.
- Two HTTPS GETs target only `checkip.amazonaws.com:443`, immediately before and
  after one fresh MongoDB client connection attempt. HTTPS uses IPv4, certificate
  verification, no redirects, no application authentication headers, a 1.5-second
  total deadline and a 64-byte response limit. Non-200, encoded, oversized and
  invalid-address responses fail closed. No application secrets reach this service.
- The MongoDB client uses the existing URI and existing 5-second selection timeout
  and pool-size setting. Existing driver instrumentation observes that attempt;
  there are no custom TLS settings, extra retry loops or automatic probes. The
  temporary client is closed afterwards.
- Addresses and rule snapshot exist only in request-local memory. Responses/logs
  contain rule-match booleans, before/after equality and existing fixed driver
  categories/stages. No raw identifiers, errors or comparison inputs are logged.

## Operator workflow

1. Verify the published commit, public health, and unauthorized rejection without
   consuming the observer. Do not run exploratory authenticated requests.
2. Refresh the authorized Atlas Network Access page read-only; privately extract
   the three active rules for the correct project into operator-session memory.
   Suppress screenshots and raw UI/accessibility output. Do not save identifiers.
3. Call `runEgressObservation(rules)` from `scripts/run-egress-observer.mjs` in that
   private session. The helper reads the existing local key, signs the fresh
   snapshot and makes exactly one request to the fixed production function. It
   returns only projected, sanitized results and never writes comparison inputs.
4. Discard the in-memory snapshot. Report only status categories and booleans.
   Do not retry on failure or reset the gate without separate owner approval.

## Interpretation and next action

HTTPS egress can differ from MongoDB egress because routing/NAT may depend on the
destination or socket. Equal before/after observations do not prove that the
MongoDB socket used that address or that future function egress will be stable.
An unmatched address supports an access-list mismatch hypothesis; it does not
alone confirm the cause of a MongoDB TLS rejection. A matched address likewise
does not disprove a mismatch on MongoDB egress.

If unmatched and the driver still fails, request separate approval for a short,
automatically expiring, single-IP experiment with explicit rollback. No Atlas
change is authorized here. Even a successful experiment does not make transient
Netlify egress a durable production solution. If an allowed, independently
correlated MongoDB source still fails, obtain provider-side rejection evidence
before changing application TLS or infrastructure.

Netlify documents fluctuating default function egress and reserves static egress
for an Enterprise add-on. No paid feature is enabled by this patch. The one small
Blobs marker uses the site's existing included service; no billing change is made.

## Validation

The test suite covers the exported Netlify handler, auth before parsing/probing,
Buffer/base64 payloads, integrity/freshness, one-use replay rejection, fail-closed
atomic storage, fixed HTTPS options/certificate verification, redirect rejection,
response bounds, timeouts, CIDR boundaries, changed observations and disclosure
canaries. Existing API, driver/TLS and security regressions remain included.
Validation before deployment: TypeScript and configured build check PASS; local
esbuild observer bundle PASS; all 23 regression/security tests PASS; dependency
audit zero vulnerabilities; secret scan of all seven proposed files zero findings;
Git diff whitespace check PASS. The restricted sandbox initially prevented Node's
Windows user lookup and registry access; the authorized checks passed outside it.
